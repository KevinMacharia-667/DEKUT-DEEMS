# Deploying Tukio (free plans)

| Piece | Platform | Free-plan notes |
| :--- | :--- | :--- |
| Frontend (React static site) | **Render** static site | Always on |
| Backend (FastAPI + recommender) | **Render** web service | Sleeps after ~15 min idle; first request then takes ~1 min |
| Database (PostgreSQL) | **Neon** | 0.5 GB; suspends when idle and wakes in about a second |

Everything for Render is described in [`render.yaml`](../render.yaml) at the repository root (a Render "Blueprint").

> **Keep secrets out of git and out of chat.** The Neon connection string and seed password go only into Render's environment settings or your own terminal session.

## 1. Push the code to GitHub

Render deploys from your GitHub repository, so push the latest `main` first.

## 2. Create the Neon database

1. Sign up at **neon.com** and create a project. Pick the region closest to your Render region (e.g. *AWS Europe Central (Frankfurt)* with Render *Frankfurt*).
2. On the project dashboard click **Connect** and copy the connection string. It looks like
   `postgresql://USER:PASSWORD@ep-xxxx.eu-central-1.aws.neon.tech/neondb?sslmode=require`.
   Keep `?sslmode=require` on the end.

## 3. Create the Render services from the Blueprint

1. Sign up at **render.com**, then **New → Blueprint**, connect your GitHub account and pick this repository. Render reads `render.yaml` and proposes two services: `tukio-api` and `tukio-web`.
2. It asks for the values marked `sync: false`:

   | Variable | Service | Value |
   | :--- | :--- | :--- |
   | `DATABASE_URL` | tukio-api | the Neon connection string from step 2 |
   | `CORS_ORIGINS` | tukio-api | `https://tukio-web.onrender.com` |
   | `VITE_API_BASE_URL` | tukio-web | `https://tukio-api.onrender.com` |

   `JWT_SECRET` is generated by Render automatically; `APP_ENV=production` makes the backend refuse to start without it.
3. Click **Apply**. On first boot the backend creates all tables in Neon.
4. **Check the real URLs.** If a name was taken, Render adds a suffix (e.g. `tukio-api-x1y2.onrender.com`). Then update:
   - `CORS_ORIGINS` on **tukio-api** to the real frontend URL (comma-separate several URLs if needed), and
   - `VITE_API_BASE_URL` on **tukio-web** to the real backend URL, then **Manual Deploy → Clear build cache & deploy** (this value is built into the app, so the frontend must be rebuilt).

## 4. Load the demo catalogue (optional, once)

The production database starts empty. To load the seeded events and demo accounts, run the seed script **from your own computer** against Neon. It refuses to run against a hosted database unless you confirm the reset and choose a private password (the local demo password `Password123` would let anyone log in as the demo admin):

```powershell
cd backend
.\venv\Scripts\Activate.ps1
$env:APP_ENV = "development"
$env:DATABASE_URL = "<your Neon connection string>"
$env:SEED_CONFIRM_RESET = "yes"
$env:SEED_PASSWORD = "<a private password, 12+ characters>"
python seed.py
Remove-Item Env:DATABASE_URL, Env:SEED_CONFIRM_RESET, Env:SEED_PASSWORD
```

Seeding **drops and recreates every table**: run it once, before real users sign up. Event dates are spread over the 60 days after the moment you seed.

## 5. Check it works

1. `https://tukio-api.onrender.com/health` returns `{"status":"ok"}` (the first call may take a minute while the service wakes).
2. Open `https://tukio-web.onrender.com`, sign up or log in, and check the feed, an event page and the dashboard.
3. **Offline (PWA) check:** in Chrome DevTools → Application → Service workers, confirm `sw.js` is activated; then Network → Offline and reload. The app shell should still load.

## Living with the free plans

- **Cold starts:** open the site a few minutes before a demo or presentation so the backend is awake.
- **Neon storage:** 0.5 GB is far more than Tukio needs for a pilot.
- **Limits change:** confirm current free-tier terms on render.com and neon.com.

## Notes

- **Schema:** tables are created from the SQLAlchemy models at startup (`Base.metadata.create_all` in `main.py`). The Alembic history in `backend/alembic/` is incomplete (it starts with migrations that assume the tables already exist), so **do not run `alembic upgrade head`** against a fresh database. Future schema changes to a live database need a proper baseline migration first.
- **Survey import against production:** `python survey_import.py ...` reads the event catalogue from `DATABASE_URL`, so set it to the Neon string to match survey events against the deployed catalogue.
- **Service worker and API:** the frontend registers `sw.js?api=<backend origin>`, so the worker recognises API calls on the backend's domain (personalised requests are never cached) and ignores other cross-origin requests.
